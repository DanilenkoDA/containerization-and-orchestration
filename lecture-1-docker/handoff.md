## Что уже понято

Не переспрашивать.

- PID namespace даёт свою таблицу PID. Снаружи номер хостовый, внутри тот же процесс может быть PID 1. `ps` читает `/proc`. `--mount-proc` монтирует новый procfs уже из нового PID namespace. Без него `ps` показывает процессы хоста.
- Namespaces не лимитируют RAM и CPU. Это cgroup.
- `/eat` за `memory.max` при `memory.swap.max=0` приводит к OOM: ядро шлёт SIGKILL процессу этой cgroup. Соседние группы живы. Пока swap для группы безлимитный, страницы уходят в swap, `memory.events` растит `max`, а `oom_kill` остаётся 0.
- `cpu.max` = `квота период` в микросекундах. `50000 100000` — 50 мс из каждых 100 мс. `/burn` не убивает процесс. `nr_throttled` считает периоды, `throttled_usec` — микросекунды простоя.
- `pids.max` не убивает живущих. Лишний `fork` получает EAGAIN. `pids.events` поле `max` считает отказы. `cgroup.procs` — список PID процессов группы, по одному на строку. `pids.current` считает задачи, включая потоки.
- `date -s` проверяет `CAP_SYS_TIME`. `ip link add` проверяет `CAP_NET_ADMIN`. `--drop` выкидывает бит из bounding set, вернуть его нельзя.
- `--user` создаёт user namespace. Часы хоста ему не принадлежат, поэтому `date -s` внутри такого `unshare` не работает ещё до `capsh`.
- Seccomp — BPF-фильтр в ядре на входе в syscall, после перехода в режим ядра и до проверки прав и capabilities. `defaultAction: SCMP_ACT_ALLOW` пропускает всё, чего нет в списке.
- `ip link set DEV netns PID` переносит интерфейс в net namespace этого процесса. PID берётся из PID namespace вызывающего. `unshare` сам входит в новый net namespace, поэтому в команду идёт его хостовый PID. Число `1` с хоста — это init хоста, конец кабеля останется на хосте.
- В `cgroup.procs` пишется хостовый PID. Внутренний PID 1 туда не подходит.
- `capsh --drop` в скрипте стоит после `ip addr` (нужен `CAP_NET_ADMIN`) и до `exec` `api`.
- Docker по умолчанию не создаёт user namespace: uid контейнера и хоста общие, root внутри — root снаружи. PID namespace при этом свой.
- Пустые `CapDrop` и `SecurityOpt` в `docker inspect` значат только «в команде флага не было». Дефолты видны в `/proc`: короткая маска capabilities и `Seccomp: 2`.
- `mem=0` и `cpu=0` — cgroup есть, квоты нет.
- Вторая сборка `lab1-api:scratch` взяла все 8 шагов из кэша. `golang:1.22` не скачивался, образ уже был локально (`1cf6c45ba39d`).

## Как запускалось

Скрипт запускать от пользователя `dadanilenko`, не из `sudo su`. Иначе `--map-root-user` сопоставит root с uid 0. `sudo` внутри скрипта используется только для cgroup и `ip`.

На ВМ стоит `docker.io`. Группа `docker` без нового логина не действует, команды шли через `sudo` / root-шелл. Контейнер `lab1-api` публикует `127.0.0.1:8081` → 8080. Образ толстый.

Старые ручные `unshare` и `veth-host` студент сносил (`kill`, `ip link del`). Перед новым запуском скрипта, если `veth-lab` занят, его надо удалить, иначе `ip link add` падает.

`ps -o pid=` дополняет номер пробелами. В `"/proc/$pid"` из-за этого получалось `/proc/ 123/status`. Пробелы снимать через `tr -d ' '`.

## Сравнение скрипта и docker run

Это уже разобрано, в отчёт студент своими словами ещё не перенёс.

Совпадает: процесс внутри PID 1, снаружи обычный PID. Свои pid, net и mount namespace. Своя cgroup.

Скрипт жёстче по user namespace (снаружи uid 1000) и по квотам (память, cpu, pids, swap 0).

Docker жёстче по правам: дефолтный набор capabilities (`CapBnd 00000000a80425fb`, без `NET_ADMIN`, `SYS_ADMIN`, `SYS_TIME`) и seccomp (`Seccomp: 2`). В скрипте снят только `CAP_SYS_TIME`, seccomp нет.

Только у Docker в этом запуске: bridge, публикация порта `-p`, корень из образа. Квот памяти и CPU у `docker run` без `-m` и `--cpus` нет, хотя cgroup `docker-….scope` есть.
